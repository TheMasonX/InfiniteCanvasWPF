## 2. Verification of Shipped Work — Diff-Level Findings

### 2.1 `ICW-P0-ACTIVECOUNT` — confirmed fixed, but two residual issues surfaced

**The core fix is correct.** Diffing `TileWorkCoordinator.cs`: `StartWorkItem`'s success path now decrements `_activeCount` unconditionally in the same lock block regardless of `wasCanceled` (previously only on the non-canceled branch); `HandleWorkStopped` now decrements unconditionally even when `_disposed` or already-canceled (previously it early-returned without decrementing in those cases); `CancelWorkItem`'s `wasRunning` branch no longer touches `_activeCount` at all — it only calls `item.CancelWork()` and leaves the decrement to whichever worker-termination path runs later. I traced all three call paths (success, `OperationCanceledException`, generic `Exception`) and confirmed **exactly one decrement occurs per physically-started work item**, regardless of whether it completes, is canceled while queued, or is canceled while running. New tests (`CancelAll_...`, `Dispose_...`) were correctly adapted to poll (`Is.EqualTo(0).After(2, 100)`) rather than assert synchronously, which is the right response to the decrement now happening asynchronously at worker-exit instead of at cancel-request time. **Confidence this specific bug is fixed: 92%.**

**Residual issue A — `ReleaseReservation` is now called twice for "canceled while running" items (not a new bug, but a newly-relevant one).** `CancelWorkItem` still unconditionally executes `_items.Remove(key); ReleaseReservation(key);` at the end of the method (lines 485-486 in the new file), regardless of `wasRunning`. For a running item, the worker's eventual termination (via the `OperationCanceledException` catch → `HandleWorkStopped`) *also* calls `ReleaseReservation(item.CacheKey)` (line 450) once it actually stops. Today `ReleaseReservation` is only a diagnostic counter (`Interlocked.Increment(ref _reservationReleases)`, still unchanged — `ICW-P0-LEASE-RELEASE` has not landed), so this double-call only inflates a diagnostics number, not a real budget release — **harmless today, but a live double-free hazard the moment `ICW-P0-LEASE-RELEASE` ships an `IDisposable` lease**, unless that ticket's implementation also removes the redundant call in `CancelWorkItem`. **This should be called out explicitly in `ICW-P0-LEASE-RELEASE`'s acceptance criteria, not left as an implicit assumption.** Confidence: 85% (mechanism fully traced; "harmless today" confirmed by reading `ReleaseReservation`'s current body).

**Residual issue B — `_items.Remove(key)` at cancel-request time (not at physical termination) can admit a duplicate, fully independent worker for the same cache key.** Because `CancelWorkItem` removes the key from `_items` synchronously when cancellation is *requested* (not when the physical `Task.Run` body actually exits), a fresh `Request()` for the same key — e.g., the user pans away and back to the same tile within the window where the old, canceled worker is still finishing a slow GDI+ call — will not coalesce against the still-running old item (since `_items.TryGetValue` now returns false for that key). It will start a **second, fully independent `Task.Run`** for the same tile/mip, correctly incrementing `_activeCount` again (so the concurrency *ceiling* invariant this fix set out to protect is not violated), but this means duplicate physical GDI+/noise work for the same tile can run concurrently. `SampleImageTile`'s epoch-based completion guards (`OnCoordinatorPixelsGenerated`/`OnCoordinatorMipGenerated`) will safely discard whichever result loses the race — **no data corruption** — but CPU/GDI+ work is wasted, and per §2.4 of the original report (GDI+ concurrency risk), this makes the already-open `ICW-P1-GDI-CONCURRENCY` concern marginally more likely to matter in practice, not less. **Recommendation:** either (a) accept this as a known, bounded, self-healing inefficiency and document it, or (b) have `Request()`'s coalescing check also scan a short-lived "recently canceled, not yet physically stopped" set before admitting a duplicate — the latter is a real design addition, not a one-line fix, so I'd recommend (a) for now with a one-line code comment at the `_items.Remove(key)` call in `CancelWorkItem` explaining the tradeoff, and revisit only if `ICW-133`'s benchmark work surfaces measurable duplicate-generation overhead. Confidence: mechanism 85% (fully traced), practical frequency during normal use 60% (plausible but not empirically observed).

### 2.2 `ICW-100` (RenderRequestTracker) — wiring confirmed correct, but the guard is currently inert

Diffing `MainWindow.xaml.cs` confirms `BeginRequest()` is called before the background `Task.Run`, `IsCurrent(requestVersion)` gates the `PublishFrame` call, and `Advance()` runs after a successful publish — exactly matching my original §3.4 recommendation and the handoff's description. **However:** `RenderFrameAsync` is only ever invoked through `DispatchRenderFrameAsync`, which is only ever invoked through `_renderAction.RequestAsync()` (a `CoalescingAsyncAction`). I re-read `CoalescingAsyncAction.ProcessAsync` (unchanged this sprint) and confirmed its `while(true)` loop `await`s each `_action(token)` call to full completion before checking `_requested` again for the next one — **meaning two `RenderFrameAsync` executions can never be in flight at the same time under the current call graph.** Given that, `_renderRequestTracker`'s version counter can only ever be advanced by the same single, serialized call path that checks it — there is currently no scenario in which `IsCurrent(requestVersion)` can observe `false`. **The guard is real, correctly wired, and will do its job the moment anything changes this serialization** (e.g., a future refactor that fires `RenderFrameAsync` directly from multiple triggers, or `ICW-100`'s own stated goal of sharing this epoch with the tile-level guard in a context where that assumption no longer holds) — but as of this commit, it is dead code in the sense that no test or manual reproduction could currently make it reject a frame. This is not a defect to "fix" so much as a fact worth recording so nobody spends time debugging "why doesn't stale-frame rejection ever trigger in my logs" later, and worth flagging if `ICW-143`'s future prefetch/priority work ever considers calling `RenderFrameAsync` from a second path. Confidence: 80% (the serialization argument is fully traced through both files; residual uncertainty is whether some other, not-yet-found call path into `RenderFrameAsync` exists elsewhere in the 1677-line file).

### 2.3 `ICW-143` (viewport culling) — shipped correctly for the tested paths; one code path has zero test coverage

`ViewportInterestSet` (new record struct in `BackgroundTileContracts.cs`), `TileWorkCoordinator.PublishInterestSet`, and the priority-aware `DrainQueueWithLivenessCheck` were all diffed and read in full. The design is sound: `PublishInterestSet` only culls *queued* (not running) items lacking interest-set membership, using the existing `RemoveClaimant`/`CancelWorkItem` machinery rather than new state — a good reuse of existing correctness guarantees rather than parallel logic. The re-enqueue loop in `DrainQueueWithLivenessCheck` (scan past non-visible queued items to find and promote a visible one, then restore ordering for the rest) is logically correct on inspection: it preserves relative order of non-promoted items and always places the originally-dequeued item back at the front.

**Test coverage gap:** all four new coordinator tests (`PublishInterestSet_CancelsNonVisibleQueuedItems`, `DrainQueueWithLivenessCheck_PromotesVisibleOverNonVisible`, plus the two Phase 0/1 liveness tests) use `maxConcurrency: 1` or `2` with **at most one item ever sitting in the queue at a time**. The scan-ahead loop's actual raison d'être — walking past *multiple* non-visible queued items to find a visible one further back — is never exercised by any test. A regression that broke the re-enqueue ordering (e.g., losing an item, duplicating one, or reversing order) would not be caught today. **Recommend adding one test**: queue 3+ items where the visible one is *not* first or second in the queue, assert (a) the visible item is promoted, (b) all non-promoted items are still present afterward in original relative order, (c) none are duplicated. Confidence this gap exists: 90% (directly confirmed by reading every test in the diff).

### 2.4 `ICW-P0-SPATIAL-INDEX-SAFETY` — fix confirmed correct; note on true severity (consistent with original report)

`LiveSpatialIndexService.Query` now does `return results.ToArray();` instead of `return results;`. Confirmed via diff. As I noted in the original audit (§2, E16/E17), the actual pre-fix risk here was narrower than the ticket implied: `results` was always a fresh `List<T>` constructed per call (never a stored/shared reference), so a caller mutating the old returned list could never have corrupted `LiveSpatialIndexService`'s internal state — the risk was a **contract/type-safety** one (an `IReadOnlyList<T>`-typed return that could be downcast and mutated), not a **data-corruption** one. The fix is good practice and correctly closes the contract gap; just don't let this get recorded in a tracker as "fixed a snapshot-corruption bug" when it was "hardened an interface contract" — the distinction matters for anyone assessing how much risk existed in production before today. Confidence: 88%.

### 3.4 `ICW-P1-COOPERATIVE-CANCEL` — now more valuable to implement than before

Original finding stands: no cancellation checks exist anywhere in `SampleImageGenerator`'s generation hot path. What's changed: previously, adding `token.ThrowIfCancellationRequested()` calls into `GenerateMonochromeMipPixels`/`ApplyMipDetails`/`ApplyDetailsWithGdiPlus` would have been **inert**, because the token flowing in was always `CancellationToken.None` (it can never be canceled). Now that `ICW-P1-CLAIMANT-TOKENS` wires a real per-frame token through `SampleImageTile`'s factories into the coordinator, that same token reaches `item.Factory(item.WorkToken)` in `TileWorkCoordinator.StartWorkItem` — but I re-checked: `WorkToken` is the coordinator's own **work-level** token (`TileWorkItem._workCts`, linked to `_disposeCts` and canceled via `CancelWork()` when the last claimant leaves), not directly the claimant token itself — the claimant token's only effect today is triggering `RemoveClaimant` via its `Register()` callback (in `TileWorkItem.AddClaimant`), which in turn can lead to `CancelWork()` if it was the last claimant. So the causal chain claimant-token-fires → `WorkToken` gets canceled → factory's `token` parameter observes cancellation **does now work end-to-end** as of this sprint, whereas before `ICW-P1-CLAIMANT-TOKENS` landed, the claimant token could never fire (it was `None`), so `WorkToken` could only ever be canceled via explicit `RemoveClaimant`/`CancelAll` calls, not via frame supersession. This is exactly the dependency the original report's §3.6 anticipated ("depends on §3.5 landing first, since today's `CancellationToken.None` makes any checks here inert") — **that dependency is now satisfied.** Implementation plan unchanged from the original report; priority raised since it will now have real, testable effect (a stale frame's tile generation can genuinely be interrupted mid-GDI+-call once these checks exist, not just theoretically).
