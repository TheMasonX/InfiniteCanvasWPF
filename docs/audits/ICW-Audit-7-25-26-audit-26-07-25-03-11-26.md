## Executive summary

This codebase is in good shape for a greenfield WPF inspection canvas, but the remaining risk is concentrated in a few places: shutdown/fault visibility, render-shell churn, brittle annotation feature contracts, and a few mismatched spatial boundary assumptions. The task tracker already covers most of the known architectural debt, which is good; the main risk now is letting those open items fragment into duplicate work instead of finishing the highest-leverage slices first. fileciteturn19file0turn66file0

The strongest theme is that the system is functionally coherent but still too much logic sits in `MainWindow`, while the rendering and async coordination paths still suppress important exceptions in a few places. The repo already has explicit backlog items for the bigger pieces of this (`ICW-014`, `ICW-018`, `ICW-019`, `ICW-021`, `ICW-022`, `ICW-023`, `ICW-031`, `ICW-032`, `ICW-033`, `ICW-035`), so the right move is to finish those items rather than open parallel duplicates. fileciteturn19file0turn66file0

## Findings and recommendations

### 1) Fault visibility is still too easy to lose in teardown and coalesced work
`CoalescingAsyncAction` reports action faults through an optional callback, but `ReportActionFault` swallows any exception thrown by that callback. `SerilogHost.Shutdown()` also catches and ignores all errors. That means a failure in the reporting path, or a cleanup-time failure, can vanish without any direct signal. fileciteturn23file0turn62file0

**Why it matters:** the app is already using many `async void` UI handlers and a coalesced render loop, so fault visibility is a correctness issue, not just a logging preference. The current design makes it easier for shutdown-time or render-time problems to fail silently. fileciteturn36file0turn41file0turn42file0turn47file0

**Recommendation:** keep the callback-based reporting model, but remove silent suppression in the reporting path. At minimum, the fault reporter should fall back to `Debug.Fail`, `Trace`, or a last-resort logger write if the main sink throws. Fold the broader UI crash-safety work into `ICW-014`; treat the coalescer/reporting path as a subcase of that work rather than a separate program. fileciteturn19file0turn66file0turn23file0turn62file0

### 2) `MainWindow` still owns too many responsibilities
`MainWindow.xaml.cs` is handling generation, spatial state, camera policy, render scheduling, cache policy, overlay creation, selection state, settings, and shutdown sequencing in one place. The code is functionally organized, but the class is doing too much and is still the primary source of brittle coupling. fileciteturn36file0turn41file0turn42file0turn43file0turn47file0turn49file0

**Why it matters:** this raises change cost, makes unit testing harder, and keeps UI-thread behavior mixed with pure policy code. The repo already acknowledges this in `ICW-022` and the low-risk cleanup bucket in `ICW-023`. fileciteturn19file0turn66file0

**Recommendation:** extract three seams first: camera/zoom policy, generation-validation/settings policy, and viewport-to-pixelometer lookup. Keep the UI layer as a thin event dispatcher. That gives you the biggest testability gain with the least risk. fileciteturn20file0turn22file0turn59file0turn36file0

### 3) The frame shell and overlay visuals are still rebuilt every frame
`BuildFrameVisual` creates a fresh root `Grid`, optional `Image`, tile-grid `Canvas`, annotation `Canvas`, per-annotation `Border`, label `Border`, and supporting brush objects on each render. `BuildTileGridLayer` also reconstructs every line every frame. The selected outline animator is then re-applied to newly created visuals each time. fileciteturn41file0turn45file0

**Why it matters:** this is the main source of allocation churn and animation reset behavior. It also makes continuity bugs more likely because selection state is tied to ephemeral visuals instead of retained elements. The tracker already flags this under `ICW-007`, `ICW-019`, and `ICW-028`. fileciteturn19file0turn66file0

**Recommendation:** retain a frame shell and pool overlay elements before optimizing pixel math further. If you do only one UI-performance slice next, make it this one. It is the clearest leverage point for both allocations and animation continuity. fileciteturn41file0turn45file0

### 4) Annotation feature access is still brittle
Annotation features are stored in a string-keyed dictionary and then read back with literal keys such as `"Confidence"` and `"Severity"` in tooltip and feature-grid paths. That is a classic primitive-obsession / implicit-contract smell: the compiler cannot help if a key changes or a feature is missing. fileciteturn34file0turn48file0

**Why it matters:** the UI is already presenting these values as first-class semantics, so the runtime dictionary is an unnecessary weak point. This is already called out by `ICW-031`. fileciteturn19file0turn66file0

**Recommendation:** move to a typed annotation metrics model and adapt the display helpers to that model. Preserve the current formatting behavior, but stop using string lookups in the hot UI path. fileciteturn34file0turn48file0

### 5) Spatial boundary semantics are not fully unified
`SpatialBounds.Intersects` uses inclusive edge comparisons, while `TileGridIndexLookup` and `SampleImageTile.TryGetPixelValue` use half-open bounds checks on right/bottom edges. That is a subtle but important semantic mismatch, especially near tile boundaries and selection edges. fileciteturn21file0turn22file0turn34file0

**Why it matters:** the repo is already using edge-sensitive math in viewport lookup, annotation placement, and hit-testing. Small mismatches here can show up as off-by-one selection bugs, duplicated edge hits, or “why did that pixel/annotation disappear on the border?” reports. `ICW-033` already tracks the larger policy question. fileciteturn19file0turn66file0

**Recommendation:** define one boundary policy and apply it everywhere. The safest approach is to document it once in the core spatial primitives and make every helper follow that policy instead of re-deriving its own edge rules. fileciteturn21file0turn22file0turn34file0

### 6) Some policy thresholds are still hard-coded in the UI/render path
The viewport clamp uses `4096` directly in multiple places, and the zoom policy uses `double.Epsilon` as the “no change” threshold. Those values are not obviously wrong, but they are brittle because they embed policy directly in the caller instead of in a named rule. fileciteturn41file0turn43file0turn59file0

**Why it matters:** this is the kind of duplication that silently multiplies when the demo grows, especially if the app ever needs DPI-aware surface policy or slightly looser zoom-change thresholds. `ICW-005` and `ICW-023` already describe this general cleanup area. fileciteturn19file0turn66file0

**Recommendation:** move the dimension ceiling and zoom-change threshold into named policy constants or helper methods. Keep the current behavior, but centralize the values so you can tune them once. fileciteturn41file0turn59file0

### 7) Query contracts still push avoidable work onto callers
`ISpatialIndexService<T>` exposes only `Count` and `Query(SpatialBounds)`, and `CanvasViewportViewModel.ApplyFrame` has to special-case `LiveSpatialIndexService<T>` to get the last published timestamp. The live service also merges snapshot, publishing, and hot buffers on each query and returns a materialized list every time. fileciteturn24file0turn25file0turn37file0

**Why it matters:** count-only or summary-only consumers still pay for list materialization, and the view model depends on a concrete implementation to surface metadata. That is a mild abstraction leak and a maintainability smell, even though the current design is understandable. This aligns with `ICW-032` and the still-proposed live-index ADR follow-up. fileciteturn19file0turn64file0

**Recommendation:** add a count/summary-oriented path or metadata interface before the query paths become more varied. Do not widen the interface unless you need to; add the smallest compatible contract that removes the special-case concrete cast. fileciteturn25file0turn37file0
