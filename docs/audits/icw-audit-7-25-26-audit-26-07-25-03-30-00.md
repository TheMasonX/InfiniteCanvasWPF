## Findings and recommendations

### 1) Failure observability is too weak in several critical paths
**Severity:** High  
**Confidence:** 95%  
**Backlog overlap:** ICW-014, ICW-029, partially ICW-038

`OnLoaded` catches `Exception` and only sets `LoadingOverlay.Text` / `StatusText.Text`, so the app loses stack trace detail on startup failures. `SerilogHost.Shutdown()` swallows every exception. `CanvasUserSettingsStore.Load()` returns defaults for IO, auth, or JSON failures without logging. `SampleImageTile.EnsurePixelsGenerationStarted()` catches all generation exceptions and only raises a generic failure event with no attached exception payload. fileciteturn25file0turn22file0turn41file0turn46file0

**Impact:** Reproducibility drops fast when a failure only leaves a status label or an empty fallback. It also makes “works on my machine” bugs far harder to isolate.  
**Recommendation:** Centralize exception logging for startup, settings load, tile generation, and shutdown. Keep the user-safe message, but always log the exception object and context. If you keep swallowing on close, do it only after logging.  
**Implementation guidance:** Add a small helper that captures `Exception`, operation name, and relevant IDs/state; use it from `OnLoaded`, `CanvasUserSettingsStore.Load`, `EnsurePixelsGenerationStarted`, and `Shutdown`.

### 2) Boundary semantics are inconsistent and create edge bias
**Severity:** High  
**Confidence:** 92%  
**Backlog overlap:** ICW-033, ICW-060, ICW-035

`SpatialBounds.Intersects()` is inclusive on both sides. `TileGridIndexLookup.TryGetTileIndex()` and `SampleImageTile.TryGetPixelValue()` are half-open on right/bottom edges. `GenerateAnnotations()` also prevents placement against the right and bottom edges because it uses exclusive upper bounds for the local random coordinates. Those three choices are not aligned. fileciteturn35file0turn68file0turn46file0turn67file0

**Impact:** This can produce subtle off-by-one selection bugs, inconsistent hit testing, and visibly biased annotation placement near tile borders.  
**Recommendation:** Pick one policy for the repo and enforce it everywhere. For this kind of tiled raster scene, half-open world bounds are usually the cleaner choice, but the important part is consistency. Then update the placement math and boundary tests to match.  
**Implementation guidance:** Add edge-coordinate tests for the exact top-left, bottom-right-1, and bottom-right boundary cases in both tile lookup and annotation placement.

### 3) `GenerateSet` has an implicit “round up to full row” contract when `rows` is omitted
**Severity:** Medium  
**Confidence:** 88%  
**Backlog overlap:** none obvious; related to ICW-015 / ICW-030 only as adjacent generation-contract work

When `rows` is null, `GenerateSet()` computes `rowCount = ceil(imageCount / columns)` and then returns `columns * rowCount` tiles. That means callers asking for 3 images with 2 columns get 4 tiles, not 3. The tests verify the explicit-rows case, but not the omitted-rows rounding behavior. fileciteturn67file0turn75file0

**Impact:** This is a hidden contract. It may be intended, but it is not obvious from the signature, and it is easy for a caller to assume `imageCount` is exact in all cases.  
**Recommendation:** Either rename the parameter/behavior to make the rounding explicit, or tighten the method so `imageCount` is always exact and derive rows another way. Add a regression test for the omitted-rows case either way.  
**Implementation guidance:** If the current behavior is intentional, document it directly in XML docs and the README so the contract is not rediscovered by accident.

### 4) `MainWindow` is still a god object and the frame tree is rebuilt per render
**Severity:** High  
**Confidence:** 97%  
**Backlog overlap:** ICW-022, ICW-028, ICW-007, ICW-019

`MainWindow.xaml.cs` owns rendering, generation, zoom policy glue, pixel sampling, settings persistence, event wiring, cache control, selection behavior, and shutdown sequencing. `BuildFrameVisual()` constructs a fresh `Grid`, `Canvas`, `Border`, `Rectangle`, label border, and overlay lines every frame. That is exactly the kind of UI churn and architectural coupling the backlog already calls out. fileciteturn25file0turn26file0turn27file0turn28file0turn29file0turn30file0turn31file0turn32file0turn33file0turn64file0turn65file0

**Impact:** The code is harder to reason about, harder to test, and more likely to accumulate accidental state coupling. The allocation churn also makes it harder to keep animation and frame timing smooth.  
**Recommendation:** Extract pure helpers first, then extract render-shell ownership. The cleanest next slice is: zoom math, generation validation, and pixelometer lookup into small testable classes, then a persistent frame shell for raster/overlay reuse.  
**Implementation guidance:** This is already aligned with ICW-022 and ICW-028. Do not create parallel tickets; continue those slices instead.

### 5) Annotation feature handling is brittle because of string-keyed contracts
**Severity:** Medium  
**Confidence:** 94%  
**Backlog overlap:** ICW-031, ICW-035

Annotations store features in `IReadOnlyDictionary<string, double>`, generator code writes `"Confidence"` and `"Severity"`, and the tooltip/UI reads those same string keys directly. That is a refactor hazard and an implicit contract that can break silently if any key changes. fileciteturn67file0turn27file0turn31file0turn46file0

**Impact:** Typing mistakes and future schema evolution become runtime issues instead of compile-time failures.  
**Recommendation:** Replace the string dictionary with a typed model or a small feature record.  
**Implementation guidance:** If you need a bridge period, keep the dictionary internally but expose typed accessors first, then remove direct key lookup from the UI.

### 6) Live spatial publishing has a hidden dropped-update contract
**Severity:** Medium  
**Confidence:** 74%  
**Backlog overlap:** adjacent to ICW-032 / ICW-060

`LiveSpatialIndexService.PublishSnapshotAsync()` returns immediately when a publish is already in progress. That means concurrent publish requests are not queued; they are effectively dropped unless the caller retries later. The code may be intentionally serializing snapshot work, but the contract is implicit. fileciteturn53file0

**Impact:** Under bursty updates, consumers may see stale data longer than expected if they assume every request eventually publishes.  
**Recommendation:** Either document this as an intentional “single-flight” behavior or change it to queue a follow-up publish automatically.  
**Implementation guidance:** If you keep the single-flight model, expose that in the interface remarks and in the README/ADR so future callers do not misuse it.

### 7) The renderer / pixelometer sampling contract is inconsistent
**Severity:** Medium  
**Confidence:** 85%  
**Backlog overlap:** ICW-035

The renderer blends defect patches and grayscale in one way, while `UpdatePixelometer()` computes a background value plus defect value separately and shows the result as `baseValue - defect/2`. That is a contract mismatch between the visible frame and the readout logic. fileciteturn29file0turn48file0turn33file0

**Impact:** The UI can tell the user one thing while the rendered pixel is showing another.  
**Recommendation:** Extract a single shared blend/sampling helper and use it in both the renderer and the pixelometer readout.  
**Implementation guidance:** This is already a tracked backlog item; reuse ICW-035 rather than creating a duplicate.

### 8) A few dead abstractions are still present
**Severity:** Low-to-Medium  
**Confidence:** 85%  
**Backlog overlap:** ICW-018

`IRenderer<TScene,TOutput>` and `ViewportRenderRequest` exist but are not actually part of the active flow. That is classic unused abstraction drift. fileciteturn44file0turn45file0turn64file0

**Impact:** Unused abstractions invite divergence between “architecture on paper” and actual behavior.  
**Recommendation:** Remove them or give them a clearly documented, tested ownership boundary.  
**Implementation guidance:** The backlog already has the right shape for this; keep the work inside ICW-018.
