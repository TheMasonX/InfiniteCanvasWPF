# InfiniteCanvasWPF — Review of External Audits + "Reusable Viewport Engine" Architecture Plan

**Documents reviewed:** the external bug audit request document, the independent bug audit report document (two independent prior bug audits), the audit synthesis document (an AI assistant's synthesis of the two, 30 `ICW-M-###` findings), and the compatibility architecture plan document — actually titled internally "Supplementary Compatibility Report: Changes Needed to Make ICW Suitable as a Reusable Production Viewport Engine" — the architecture plan to evolve ICW from a demo app into a host-agnostic `ICW.Core`/`ICW.Spatial`/`ICW.Rendering`/`ICW.Resources`/`ICW.Presentation`/`ICW.Wpf`/`ICW.SampleApp` engine.
**Source cross-checked against:** the live repository at `139a8b62` (my most recently audited HEAD, still current as of this review) and my own 10 prior audit passes.
**Scope of this report, per instructions:** only genuinely new findings — validation spot-checks of the external audits' specific technical claims, plus architecture-plan feedback that draws on findings from my own audit history the plan's authors could not have had (they worked from a static source dump, not from live git history or multi-session iterative auditing).

## Part A — Validation of the External Bug Audits (spot-checks, not exhaustive)

The `ICW-M-###` master findings table (30 items) is well-organized and mostly source-backed. I did not re-verify all 30 line by line (that would just be re-auditing, not new work), but spot-checked a sample, including the ones most likely to be stale or subtly wrong:

## Part B — Architecture Plan Feedback: Blockers, Bottlenecks, and Regression Risks

The compatibility report's direction (extract a reusable `ICW.*` engine from the demo app, add immutable snapshots, lease-based resource ownership, and a proper source-adapter boundary) is sound and matches where a project like this needs to go. The following are risks specific to *this codebase's actual, current, live behavior* — visible only from the kind of iterative, multi-session auditing I've been doing, not from a static source review.

### 1. [Blocker risk] Phase 5's async `IMemoryGovernor.EvictAsync` will resurrect a reentrant-lock hazard I already found in the current code — unless Phase 6 lands first, or the design accounts for it explicitly

The plan's Phase 5 ("Resource Ownership and Surface Leases") comes before Phase 6 ("Cancellation and Scheduler Hardening"), and its `IMemoryGovernor.EvictAsync(EvictionRequest, CancellationToken)` (§11.3) is asynchronous (`ValueTask`).

I found, in the *current* codebase, that `TileCacheBudget.TryReserve`'s eviction path calls `evictedTile.ResetImageCache()`, which calls back into `TileWorkCoordinator.RemoveClaimant(...)` — which **re-enters the same `TileWorkCoordinator._lock` instance** that the *outer* call (`TileWorkCoordinator.Request`, which invoked `TryReserve` as its admission check) is still holding. This only works today because every hop in that chain is synchronous and single-threaded, and `System.Threading.Lock` happens to support same-thread reentrancy. It is not a designed lock hierarchy; it's an accident of everything currently being inline.

If `IMemoryGovernor.EvictAsync` is implemented as genuinely asynchronous (e.g., it awaits anything, or dispatches eviction notification via `Task.Run`), and eviction is triggered from inside a `TryReserve`-equivalent call that's still holding a scheduler lock (which is exactly the shape of the current admission-check flow this plan is meant to replace), the *same* call chain becomes a **hard cross-thread deadlock** instead of a harmless same-thread re-entry — because the resumed continuation after an `await` is not guaranteed to be the same thread that entered the lock.

**Recommendation:** Either (a) reorder so Phase 6's scheduler/claimant rework lands before or alongside Phase 5's memory governor, with an explicit design note that eviction notifications must never call back into scheduler state synchronously from within an admission-check lock, or (b) if Phase 5 must come first, make `IMemoryGovernor`'s reservation/eviction path deliberately return *data* (e.g., "these keys were evicted") to its caller rather than calling back into the scheduler itself, so the scheduler decides what to do with that information after its own lock has been released — breaking the callback chain instead of relying on it staying synchronous forever. Add an explicit test in §18.2 for "eviction triggered while scheduler lock is held, on a genuinely multi-threaded path" — none of the current integration test list would catch this class of bug, since it only manifests under real thread-hopping, not in a single-threaded unit test.

### 2. [Design gap] Section 10's claimant model doesn't name the specific failure mode I found in the current `AddClaimant`

The current `TileWorkItem.AddClaimant` registers a `CancellationToken.Register` callback *before* adding the claimant to its tracked list. If the token is already canceled at call time (plausible under the coalescing this plan's `ViewportInterest`/`TileRequest` model explicitly enables), `Register` fires synchronously and immediately — finds nothing to remove (the entry isn't added yet) — and the claimant then gets added anyway, permanently unable to be removed via its own token again (registration callbacks fire once). This produces a "ghost claimant" that keeps a work item alive indefinitely.

Section 10.3's rule "Terminal cleanup disposes claimant registrations and linked token sources exactly once" addresses *cleanup*, but nothing in §10.1–10.4 addresses *registration-time* ordering. Since this plan's whole point is to formalize the claimant/interest model that's currently informal, this is exactly the moment to close this specific hole rather than carry the bug forward into the "hardened" version.

**Recommendation:** Add an explicit rule to §10.3: *"A claimant must be added to the tracked set before its cancellation callback is registered, or the registration and add must happen atomically, so an already-canceled token cannot fire against an empty/not-yet-present entry."* Add a corresponding unit test to §18.1: `TileScheduler_PreCanceledClaimantTokenIsRemovedNotGhosted`.

### 3. [Sequencing] Phase 2's "stale-frame rejection" has *already been built once* in this codebase and silently regressed — treat it as a re-fix with a regression guard, not greenfield work

As validated in Part A, `RenderRequestTracker` (a correct epoch-counter implementation) was built, wired in, and then silently unwired by an unrelated commit, with the backlog still saying it's done. This is directly relevant to Phase 2 ("Add stale-frame rejection") for two reasons: (a) whoever implements the *new*, more formal `RenderFrameSnapshot`-based version should look at the old `RenderRequestTracker`/its removal commit first — there may be a reason it was in the way of the scrollbar/interaction work that removed it, worth understanding before repeating it; (b) more importantly, **this specific class of regression (a correct concurrency fix silently dropped by an unrelated later commit, with no test catching it) has now happened at least once in this codebase**, which is itself evidence for a recommendation the plan doesn't currently make: add a *behavioral* regression test that fails if stale-frame rejection is ever unwired again — not just a unit test of the epoch counter in isolation (which is exactly what existed before and didn't catch the regression, since the counter class itself still worked fine; it was just no longer called).

**Recommendation:** Add to §18.2 (Integration Tests): *"Rendering a superseded frame request end-to-end (through the public engine API, not by unit-testing the epoch primitive directly) never publishes stale content"* — phrased so it fails if the wiring is ever dropped, not just if the counter logic is wrong.

### 4. [Sequencing] Don't build byte-accurate resource accounting (§11) around resources that are dead weight — remove them first

Section 11's memory governor is meant to account for "native tile, mip level, overlay/defect bitmap, mapped surface, pending work, and temporary buffers" (per the improvements doc's own ICW-M-013, which this plan is responding to). I found, independently, that the current `DrawDefectPatch` locks and samples a GDI+ `Bitmap` (`annotation.DefectBitmap`) per pixel per annotation per frame — and never uses the sampled value; the actual rendered pixel comes entirely from a separate managed `byte[]` (`DefectPixels`) via a different code path. The `Bitmap` construction, its pooling, and its (correctly-implemented, as of a later fix) disposal all exist to support a value that gets thrown away.

If §11's lease-based accounting is implemented against the *current* resource shape, it will faithfully create an `OverlayPayloadLease`/similar for this bitmap pool, count its bytes, track its lifetime, and report it in diagnostics — formalizing and giving first-class status to memory that produces zero rendered output. That's effort spent making waste observable instead of removing it, and it also means the new lease model's first real test case is a resource that shouldn't exist.

**Recommendation:** Delete the dead `DefectBitmap` GDI+ pipeline (a well-contained, low-risk change, since the "real" path already exists and works) *before* or *during* Phase 5, not after — it removes an entire resource category the new accounting system would otherwise need to model, and removes a live use-after-dispose race I separately found between scene regeneration and concurrent rendering of that same pool.

### 5. [Contract gap] The source-adapter contract (§6) needs an explicit determinism clause the current synthetic source violates today

I found, in the current `SampleImageGenerator`, that background noise is generated per-tile with `pixelSeed = options.Seed + 3 * tileIndex` — a *different* seed per tile — while world-space coordinates are correctly threaded through for continuity. For seed-sensitive noise functions (Simplex/FBM, as used here via FastNoise2), varying the seed per tile defeats worldspace-coordinate continuity entirely: two tiles sample *unrelated* fields regardless of correct coordinate offsetting. This directly contradicts this same synthetic source's own ticket's stated goal of "seamless worldspace sampling."

This matters to the plan beyond just "here's a bug": §6 (Source Adapter Contracts) defines what `IRasterTileSource`/`ITileSource` must guarantee, but as drafted it doesn't state a determinism/continuity clause at the level that would have caught this. The natural place to add it: *"A tile source's output for a given world-space region must depend only on (world coordinates, source revision) — not on how the scene happens to be decomposed into tiles (tile index, tile ID, or acquisition order). Two different tile decompositions of the same world region and revision must produce pixel-identical output where they overlap."* Without a rule like this stated explicitly, a future source adapter (including the sample app's own synthetic one, today) can silently reintroduce exactly this class of seam bug, and nothing in §18's test list would catch it — none of the listed unit/integration tests check cross-tile consistency for a given source.

**Recommendation:** Add the determinism/continuity clause above to §6.1, and add `RasterSource_OutputIsInvariantToTileDecomposition` (sample two different tile-boundary layouts of the same world region+revision, assert pixel equality in the overlap) to §18.1.

### 6. [Pattern-level risk] This codebase has a repeated, evidenced history of shipping declared-but-unwired abstractions — the plan needs mandatory enforcement tests per contract, not just structural ones

Across my prior audit sessions I independently found, at different times: `IRenderer<TScene,TOutput>` (declared, zero implementations, zero consumers); `IBackgroundTileSource` (declared as part of the mip-pyramid work, zero implementations at the time — though its owning ticket honestly says so); `RenderRequestTracker` (built, wired, then silently unwired — see finding 3); `GeneratorOptions.ImageCount`'s default value (a placeholder pixel-width constant that the code's own comment admits is meaningless); and the FIFO tile-work queue's complete absence of priority handling despite `TileWorkCoordinator` clearly being designed with future prioritization in mind. This is not one bug — it's a *pattern*: this codebase, across many sprints, repeatedly introduces interfaces/fields/mechanisms that are structurally present but not actually load-bearing.

This is directly relevant to the plan because it defines a *lot* of new contracts (`IViewportSource`, `ITileSource`, `ILayerSource`, `IOverlaySource`, `IReadbackProvider`, `ISpatialEntitySource`, `IResourceReservation`, `IResourceLease`, `IMemoryGovernor`, `ISurfacePool`, `IFramePublisher`, and more) and the test list in §18 is mostly *behavioral/scenario* tests (rapid pan/zoom, resize during publication, etc.) rather than *contract-enforcement* tests that specifically check "is this interface actually wired to something real, or does it just compile." Given this team's own track record, that's the failure mode most likely to recur at scale across a dozen new interfaces.

**Concretely, and as a live example right now**: §10.2 defines `TileRequest` with a `TilePriority Priority` field, but §10.3's Scheduler Rules only say "Queue draining is deterministic" — nowhere does the spec require that priority is actually *honored* during draining (e.g., "a higher-priority ready request is dequeued before a lower-priority ready request"), and no test in §18.1/18.2 checks it. Given the *current* live codebase's tile-work queue is a plain FIFO `Queue<T>` with zero prioritization despite an already-open ticket for exactly this, and given this plan is the direct successor to that ticket, `Priority` is at real risk of becoming exactly the kind of structurally-present-but-unenforced field this codebase has shipped multiple times before.

**Recommendation:** For every new interface/contract this plan introduces, add at least one "is this actually wired, not just implemented" test — e.g., `TileScheduler_DequeuesHigherPriorityBeforeLowerPriorityWhenBothReady` for the `Priority` field specifically, and a general project convention (perhaps a lightweight architecture test using a reflection-based check, or just a checklist item in code review) that a new public interface isn't considered "done" until something in the production path — not just a test double — calls it.

### 7. [Bottleneck risk] §12's "prefer triple-buffering" recommendation needs an explicit cross-pool memory ceiling, not just per-pool separation

§11.4 correctly requires "Surface memory is counted separately from tile memory" and "Mip memory is counted separately from native tile memory" — good, necessary, but insufficient on its own. §12.1/§12.3 separately recommends triple-buffering surfaces (up from the current double-buffering) "until presentation-retirement behavior is proven." Combined with the mip pyramid (already roughly +33% memory over native-only tiles, by construction of a standard mip chain) and §2's explicit multi-viewport goal (each additional viewport plausibly wanting its own surface pool), the total peak native memory footprint across pools could grow substantially with no single acceptance criterion in the plan bounding the *sum* — only per-pool bookkeeping. Given the existing `TileCacheBudget` was specifically built to cap total tile memory, replacing it with several independently-well-behaved-but-jointly-unbounded pools would be a regression relative to today's single ceiling, even though every individual piece is "correct" by its own local rules.

**Recommendation:** Add one acceptance criterion to §11.4: a single `IMemoryGovernor` (or equivalent top-level budget) that bounds the *sum* of tile, mip, surface, and overlay reservations across all pools and viewports, not just per-category counting — and a stress test in §18.3 that runs multiple viewports plus triple-buffered surfaces plus a full mip chain simultaneously and asserts peak memory stays within one configured ceiling.

## Summary

The bug audits are solid work with a low observed false-positive rate (flagging one, ICW-M-028, as not actually a bug). The architecture plan's direction is right, and its phased structure is reasonable. The seven items above are the risks I can uniquely see from having audited this codebase iteratively over many sessions rather than from a single source snapshot: two concrete concurrency hazards the plan's own phase ordering would walk into (findings 1–2), one piece of load-bearing history the plan should know before re-implementing something that already existed once (finding 3), one case of "don't formalize accounting around dead code" (finding 4), one concrete contract gap illustrated by a live bug in the sample source itself (finding 5), one team-level pattern risk with a specific live example already visible in the plan's own draft (finding 6), and one cross-cutting resource-budget gap (finding 7).
