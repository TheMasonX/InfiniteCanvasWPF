# Functional Requirements and Invariants Registry

This document is the canonical place for user-visible behavior requirements and invariants that have regressed more than once. It complements ADRs and tickets:

- ADRs capture architectural decisions and ownership boundaries.
- Tickets capture implementation work and delivery scope.
- This registry captures the behavioral contract that must remain true across future changes.

## Maintenance policy

- Update this registry whenever a user requirement, invariant, or regression risk is captured or changed.
- Link each entry to the relevant ticket(s), ADR(s), and any regression tests when they exist.
- If a change would alter one of these invariants, update this document in the same change so the requirement stays discoverable.

## Canonical requirements

| Area | Requirement | Related work | Notes |
| --- | --- | --- | --- |
| Zoom behavior | Uniform zoom is permitted only when neither axis is clamped. While either axis is clamped, preserve the axis-clamped transition and recover to the uniform width target only when the clamping condition no longer applies. The zoom-out to zoom-in round trip must retain width clamping rather than remain anisotropic. | ICW-044, ICW-046, ICW-072 | This is a core interaction invariant and should be treated as regression-sensitive behavior. The `xIsClamped || yIsClamped` condition is intentional and must not be changed to XOR. |
| Camera scale limits | `CameraTransform` must retain intentionally wide numerical scale limits (`MinimumScale = 0.0000000001`, `MaximumScale = 10000`). User-visible zoom limits come from viewport-size/content-bound policy and `ClampToBounds`; do not narrow these constructor defaults as a substitute for viewport clamping. | ICW-044, ICW-072 | This preserves extreme zoom navigation while keeping the actual scene navigation bounded by the viewport contract. |
| Camera viewport sizing | The render target, zoom-floor calculation, and camera clamp must use the fixed visible viewport dimensions only. Scrollbar extent or scaled-scene dimensions must never replace those dimensions. | ICW-065 | Violating this invariant can make zoom-out unreachable and allocate a smeared oversized raster. |
| Camera-native scrollbars | Viewport scrollbars are custom overlay controls derived from the captured camera and scene bounds. Their thumbs must update after pan, zoom, resize, and regeneration; thumb drag and track click must pan through the bounded camera path without participating in viewport measurement. The XAML overlay, event handlers, policy calculation, and `RenderFrameAsync` update hook are one protected feature and must remain present together. | ICW-065, ICW-079 | This enables standard scrollbar navigation without reintroducing the native `ScrollViewer` regression. `CanvasScrollbarWiringTests` guards against deleting the overlay or silently dropping its render update call. |
| Zoom UI | The zoom control should provide an integrated custom-value entry with a shared Apply/Enter workflow and clear validation feedback. | ICW-045 | Keep the custom entry compact and aligned with the existing preset flow. |
| Background tiles | The default background tile height should be taller than the baseline tile layout, and tile generation should remain non-blocking when the scene is first presented. | ICW-039, ICW-047 | Preserve first-frame responsiveness even when background imagery is generated lazily. |
| Background tile index labels | Synthetic background tile payloads should contain their stable logical tile index as dark-gray Gray8 content at the local top-left, generated alongside the circle content for every requested mip when the persisted label setting is enabled. The label must remain tied to the logical tile across mip selection/fallback, and its intentional loss of sharpness at lower resolution is part of the mip diagnostic. | ICW-130, ICW-336 | Use tile-local generation coordinates and value `16`; do not add a duplicate frame-level label pass, derive identity from visible-tile order, or make the label screen-fixed. The setting defaults to enabled and applies to every requested mip. |
| Background tile mip levels | When the viewport is zoomed out enough, the background tile system should fetch or generate a lower-resolution canonical mip rather than always use the full-resolution source. The render path must request only the selected mip, and it must request mip 0 only when the camera policy or an explicit inspection contract requires native resolution. For deterministic synthetic imagery, each requested level must be generated directly from its underlying deterministic noise: a higher-level texel averages the valid four child-grid samples from the level below without regenerating the full native image or intermediate chain. The system supports at least eight levels, each using `max(1, ceil(nativeDimension / 2^level))`, and a stable source-scoped identity plus content revision. Canvas and raster inputs remain source-agnostic: a materializer/cache resolves descriptor-plus-request contracts asynchronously, while the synchronous rasterizer receives only a validated resident payload or placeholder. | ICW-076, ICW-096, ICW-150, ADR-0005 | Direct requested-level generation is the primary mip performance requirement. Cache keys, reservations, and visible-frame pins include source ID, tile ID, content revision, and mip level; accounting uses actual resident payload bytes. Pixelometer reads use an explicit non-blocking mip-zero path until a source-neutral point-sampling contract exists. |
| Viewport-aware tile work | Tile materialization must be bounded, deduplicated by complete source/revision/mip identity, and aware of the current viewport interest set. Queued work that is no longer visible or within the configured prefetch margin must be removed or marked canceled; in-flight work must stop when it has no current claimant, while shared fills continue for remaining claimants. Visible work must outrank prefetch and stale work, and cancellation must release reservations without stale publication or UI faults. | ICW-141, ICW-142, ICW-143, ADR-0006 | Render coalescing alone is not tile-work cancellation. Keep the rasterizer non-blocking, preserve resident mip fallback, and choose concurrency/prefetch values from repeated fast-scroll evidence. |
| Deterministic tile generation | A scene master seed must derive independent deterministic random streams for each tile and annotation operation. Lazy parallel generation must not share mutable RNG state, and generating a tile concurrently must produce the same pixels as generating it serially. | ICW-050 | Use an isolated per-operation generator; do not use a shared `Random` from tile worker tasks. |
| Sparse image tiles | Sparse image tiles should be generated on demand as the viewport approaches them, and they should follow the same cache-oriented lifecycle as background image generation. | ICW-047, ICW-074 | The generation path should remain computationally acceptable and should not block the main render path. |
| Sparse tile thresholding | Sparse tiles should skip generation entirely when the projected tile size is below a configurable minimum pixel-size threshold, allowing zoomed-out views to avoid spending CPU and memory on tiny tiles. | ICW-074, ICW-136 | The threshold remains runtime-configurable and persisted with other generation settings. The demo default is the named zero-value constant `CanvasUserSettings.DefaultMinimumSparseTilePixelSize`, so background tiles remain renderable at extreme zoom-out. A positive value is an explicit opt-in suppression policy. |
| Image tile display | A visible toggle should control whether sparse image tiles are displayed. | ICW-047 | The default should remain predictable and the toggle should be discoverable in the display panel. |
| Cache policy | Cache size should be guided by pixel cost rather than simple item count, the default budget must retain at least one default-size tile, and cache status should be visible for debugging. | ICW-047, ICW-049 | This avoids overfitting cache behavior to tile counts, prevents immediate eviction of every default tile, and makes cache pressure easier to reason about. |
| Lazy tile cache admission | Cache capacity is a byte-based memoization ceiling, not a reason to evict active viewport tiles. Visible-frame tiles are protected during rasterization; requests that cannot be admitted render placeholders without retrying continuously, and failed generation releases its reservation. Eviction must fall back to un-generated tiles when no generated tiles are available, to prevent deadlock when the budget is full of tiles whose generation never completed. | ICW-064, ICW-142 | The default ceiling is 4 GiB of Gray8 source bytes and diagnostics must show byte use plus resident tile count. Un-generated tile eviction may waste in-flight coordinator work (epoch bump causes discard), but is necessary to keep the pipeline moving. |
| Tile cache capacity and metrics | The tile cache must retain many generated tiles when the configured pixel budget permits it. Runtime and benchmark paths must expose queue depth, generation, conversion/copy, eviction, cache residency, and frame timing before changing image-generation or pixel-transfer technology. | ICW-064 | Candidate 16-pattern stamping, 8bpp indexed/Gray8, SIMD/hardware, or marshalling approaches require comparable benchmark evidence before adoption. |
| Layer visibility toggles | Labels, boxes, sparse image tiles, and background images should be independently show/hide controllable at runtime and persist with the rest of the display settings. | ICW-073, ICW-082, ICW-093 | The controls are separate in the display panel. `LayerVisibilityWiringTests` guards independent load, save, and render consumption. |
| Annotation labels | Annotation labels should default to a smaller size than the old baseline, and the label mode should support either class or ID, defaulting to class. | ICW-041 | Keep labels legible without overwhelming the scene. |
| Overlay layering | Tile-grid boundaries should be drawn between the raster image layer and the annotation overlay using the same camera snapshot as the raster frame. | ICW-040 | The overlay should be camera-synchronized and non-hit-testable. |
| Sparse defect imagery | Sparse defect imagery should be rendered as grayscale bitmap content on a separate image layer without tinting or clipping to the logical annotation bounds. | ICW-042 | Preserve the original bitmap intensity and keep the defect layer distinct from annotation styling. |
| Annotation inspection | Selecting an annotation should populate a sidebar DataGrid with the annotation feature values, and the grid should clear on deselection or regeneration. | ICW-048 | This is part of the inspection workflow and should remain available in the UI. |
| Settings persistence | Display and generation settings should persist across app runs and be saved on close. | ICW-043 | Preserve user-adjusted state even after the app restarts. |
| Display settings panel layout | The display-settings content must keep a reserved inset beside its vertical scrollbar so controls and labels never render beneath the scrollbar; horizontal overflow is disabled. | ICW-094 | Preserve readable control bounds at the panel's minimum width and when the settings content becomes vertically scrollable. |
| Viewport tile transition | When zooming changes the selected background mip, a resident older mip or full-resolution payload must remain renderable until the requested replacement is complete; publication of a new payload must be atomic from the frame's perspective. | ICW-096, ADR-0005 | A missing requested mip may trigger asynchronous generation, but must not blank or replace otherwise usable image data with a placeholder. |
| External material frame identity | An external material frame must carry source-qualified session identity plus scene, layer, display, selection, and render sequence revisions. A render sequence alone is not freshness proof. Source change notifications must carry the semantic revision needed to reject stale material state. | ICW-337, ICW-339, ICW-312, ICW-328 | Keep identity value types source-neutral. Do not expose external service or application data types through `InfiniteCanvas.Core`. |
| Atomic material layer publication | Raster content, ordered material layers, visibility state, pixelometer provenance, and interactive item state must come from one accepted viewport snapshot. A rejected frame must update no visual layer. | ICW-337, ICW-340, ICW-315, ICW-317 | Preserve the persistent frame shell and composition-fenced buffer ownership while moving acceptance behind one frame plan. |
| Published payload ownership | A published frame and resident tile payload must own stable read-only input. Caller-owned lists and writable byte arrays must not mutate accepted frame or cache state after publication. | ICW-338, ICW-316A, ICW-076 | Use defensive copies or immutable read-only representations at the ownership boundary. Test mutation and concurrent reads. |
| Frame stability (no flashing) | The canvas must NEVER flash, flicker, or blank while navigating, including during fast pan and zoom. A visible tile must always render a stable image. A tile with a resident payload must always show that payload. A tile without a payload must show a stable placeholder that never oscillates. In-flight generation for a visible tile must never be canceled by a frame boundary; the work completes and publishes atomically. Content must never regress to a placeholder while the tile remains visible. | ICW-205, ICW-143, ICW-096, ICW-204, ICW-317, ICW-315, ICW-P0-BUFFER-REUSE-SYNC, ADR-0006 | HARD CONSTRAINT. Not a suggestion. Per-frame claimant-token fire must not cancel in-flight work whose cache key is still in the published interest set. Stale work for tiles that left the viewport is still canceled. Frame-token cancellation restarts visible generation every frame; this caused permanent placeholder gray during scroll. DELIVERED 2026-08-04: FrameBufferPool triple-buffering stops buffer-reuse tearing; the persistent frame shell (ICW-317) stops per-frame Viewbox child teardown flashes. ICW-315 moved the shell into `CanvasControl`; `FrameShellWiringTests` now guards that the Viewbox child is assigned exactly twice (shell attach + detach). |
| Defect overlay precedence | The defect renderer and pixelometer must resolve matching annotations in source order, with the last applicable annotation value replacing the prior value. Non-matching annotations must preserve the current value. | ICW-035 | Both paths use `DefectOverlaySampler.ResolveDisplayValue`. Overlap precedence is intentionally last-applicable-wins, not maximum-value blending. |
| Rendering CPU budget | Synthetic background generation should remain native Gray8 from generation through tile residency. It must not create a 24bpp GDI+ bitmap and immediately perform a full RGB-to-gray conversion. Direct mip-level generation and reduced work are higher priority than precomputed jitter; precomputed sequences should not be introduced without evidence that its memory-bandwidth cost beats the simpler deterministic computation on the target hardware. | ICW-097, ICW-050 | External color sources may use a separately benchmarked conversion path, but synthetic Gray8 sources must bypass it. Validate changes with focused benchmarks and preserve deterministic output contracts where tests depend on them. The optimization order is direct mip generation first, resident-data fallback second, then further hot-path tuning. |
| Performance evidence | Rendering performance claims must distinguish native noise generation, managed Gray8 normalization, circle rasterization, tile composition, cache hits/misses, mip level, sample count, and resident payload bytes. One-iteration Dry benchmarks are smoke checks only and must not support percentage claims. | ICW-132, ICW-133, ICW-134, ICW-135 | `RenderingDiagnostics` provides opt-in stage timings and per-mip lifecycle counters. Future optimization work requires repeated before/after measurements at matching dimensions, settings, cache state, and runtime/build configuration, with deterministic and visual regression coverage where raster output changes. |
| Cache diagnostics identity | Cache debug status must report the live cache instance and its actual resident, queued, generated, reserved, and eviction state rather than a fixed or stale singleton summary. | ICW-096 | Diagnostics are part of the debugging contract and must distinguish cache resets, scene regeneration, and mip variants. |

## External audit mandatory requirements

These requirements come from an external audit of the canvas system for use as a reusable production viewport engine. Meeting them is mandatory.

| Area | Requirement | Related work | Notes |
|---|---|---|---|
| Coordinator concurrency | The coordinator's `_activeCount` must represent physically executing factory delegates only. It must be decremented in the worker's terminal `finally` block, not at cancellation-request time. During a cancellation burst, the concurrency cap must be a real bound on simultaneous work, not exceeded by stale delegates. | ICW-P0-ACTIVECOUNT, ADR-0006, External audit validation §2 | Failure mode: `DefaultMaxConcurrency = 4` is not a hard ceiling during fast-scroll cancellation storms, leading to unbounded simultaneous GDI+ operations. |
| Queue drain liveness | `DrainQueue` must check claimant-token liveness before advancing past a queued item. A stale-token item must not block a usable one behind it or waste a concurrency slot. | ICW-P0-QUEUE-DRAIN, ADR-0006, External audit validation §1 | Failure mode: stranded items with stale tokens queued in front of usable ones, burning concurrency slots and degrading responsiveness. |
| Claimant token wiring | Claimant tokens must originate from the frame/viewport lifecycle, not be hardcoded to `CancellationToken.None`. Per-frame claimant advancement must use token-source replacement rather than `RemoveAllClaimants`. | ICW-P1-CLAIMANT-TOKENS, ADR-0006, External audit validation §1 | Failure mode: the coordinator's auto-remove-on-token-fire mechanism is dead code; viewport culling (ICW-143) cannot function without real tokens. |
| Tile generation recovery | A tile's generation-queued dedup flag must be reset when its claimant token fires or when its generation fails. A frame boundary must never permanently strand a tile; a later frame must be able to re-request generation. | ICW-204, ICW-142, ICW-143 | Failure mode: per-frame claimant token cancellation orphaned coordinator work without a callback, leaving `_generationQueued` / `_mipGenerationQueued` set. Tiles stayed blank until a zoom changed the mip key and created a fresh request. |
| Pixelometer readout | Pixelometer readout (`TryReadPixelValue`) must never initiate tile acquisition as a side effect of mouse movement. It must consume a published-frame snapshot or the best available resident payload only. Tile generation triggered by hover must participate in `TileCacheBudget` accounting. DELIVERED 2026-08-04: the read flows through `ICanvasSceneSource.TryReadResidentPixel`, which uses `SampleImageTile.TryGetResidentPixels` (resident payloads only, never starts generation). | ICW-P0-PIXELOMETER-READOUT, ICW-312, External audit validation §3 | Failure mode: mouse hover generates untracked, unrecoverable tile memory outside the cache budget system — cannot be evicted, grows unbounded. |
| Regeneration atomicity | `RegenerateSceneAsync` must be atomic from the user's perspective. Failure or cancellation must restore the previous scene state (tiles, spatial index, settings, displayed frame). Partial initialization must not be visible. | ICW-P0-TRANSACTIONAL-REGEN, External audit Phase 0 | Failure mode: a failed regeneration leaves the app with partially-initialized state — missing tiles, no fallback to previous scene. |
| Frame surface reuse | A retired frame surface (`InteropBitmap`) must not be modified or reassigned until WPF's compositor has confirmed it is done reading the backing memory section. | ICW-P0-BUFFER-REUSE-SYNC, ICW-318, ICW-021, ADR-0004, External audit validation §5 | Failure mode: recycled `InteropBitmap` memory section may still be read by WPF's asynchronous compositor, causing visual artifacts or access violations. DELIVERED 2026-08-04: `FrameBufferPool` holds a retired buffer for two `CompositionTarget.Rendering` passes (composition fence, ICW-318) before reuse. User-reproduced black horizontal bands during fast scroll confirmed the race. |
| Cache lease release | Cache reservations must use exactly-once release semantics enforced by `IDisposable`. `ReleaseReservation` must not be a no-op diagnostic counter. | ICW-P0-LEASE-RELEASE, External audit validation §4 | Failure mode: budget bytes are never released, causing premature eviction of other tiles. Fix must include double-dispose safety and leak detection. |
| Cooperative cancellation | Tile generation factories must be cooperatively cancellable. They must check the cancellation token at least once per expensive sub-phase (circle rasterization, noise generation, memcpy). | ICW-P1-COOPERATIVE-CANCEL, External audit Phase 1 | Failure mode: during fast scroll, GDI+ operations continue to completion even after tile is no longer visible, wasting CPU and holding concurrency slots. |
| Platform-interop concurrency | Any platform-interop drawing (GDI+, or equivalent on other platforms) used inside a generation factory must be subject to explicit physical-concurrency guarantees independent of the coordinator's admission concurrency. | ICW-P1-GDI-CONCURRENCY, ADR-0006, External audit pass 12 §2 | Failure mode: concurrent `Bitmap`/`Graphics`/`FillEllipse`/`LockBits` calls across up to N threads (unbounded during cancellation) can cause `ExternalException` or instability. |
| Settings validation unification | Every declared option field must have exactly one canonical validation function, used identically by the XAML binding path, the JSON file-load path, and any host-adapter translation path. Every declared option field must be demonstrably read somewhere in the actual render/generation call graph. | ICW-P1-SETTINGS-VALIDATION, ICW-030, ICW-099, External audit plan refinement §3 | DELIVERED 2026-08-06 (Wave N): `CanvasUserSettings.ValidateObjectsPerTile` and `ValidateMinimumSparseTilePixelSize` are the canonical functions; `IsValid`, `TryReadGenerationOptions`, and both `SampleImageGenerator.GenerateSet` overloads share them. `MinimumSparseTilePixelSize` is persisted, has a UI control, and reaches `GenerateFrozenBitmap` → `DrawTile` via `ShouldGenerateForPixelSize`. |
| Mip memory accounting | Cache byte accounting must equal the sum of resident payload byte lengths across all cached mip variants for each tile. `PixelCost` must not be a mip-0-only computation. | ICW-P1-PIXELCOST-MIPS, ICW-134, ADR-0005, External audit plan refinement §4 | Failure mode: `TileCacheBudget.UsedBytes` undercounts actual resident heap by up to ~33% once several mip levels accumulate. |
| Settings lifecycle in Phase 1 | MainWindow decomposition (Phase 1 of the compatibility plan) must explicitly include: (a) settings not silently reset on `RegenerateSceneAsync`, (b) `CanvasUserSettings.IsValid` checks all enforced bounds, (c) every persisted setting is verifiably consumed. | ICW-P1-SETTINGS-SCOPE, ICW-022, External audit validation §6 | Without this, a team could complete every migration phase and ship known settings-persistence bugs intact. |
| Migration sequencing | During the 8-phase, 5-assembly migration, concurrent feature work must either freeze for Phases 1-2 or be built against emerging contracts (strangler-fig pattern). The target must not move faster than the migration. | ICW-P0-MIGRATION-GUARD, ADR-0006, External audit plan refinement §5 | Risk: new feature work landing mid-migration built against old `MainWindow`-owned contracts creates more migration surface later. |
| Static claimant identity | Claimant identity for tile work must be per-tile or per-viewport-frame, not a static `DefaultCoordinatorClaimant` shared by all tile instances. `RemoveAllClaimants(GetClaimantId())` must only affect the intended tile/viewport. | ICW-P1-CLAIMANT-TOKENS, External audit pass 6 §2 | Failure mode: calling `RemoveAllClaimants(GetClaimantId())` with the current static claimant would cancel every tile's in-flight generation. |

## Sprint 1 Wave A additions (2026-07-30)

| Area | Requirement | Related work | Notes |
|---|---|---|---|
| Frame-level stale render rejection | `RenderFrameAsync` must check a render-request epoch before publishing a frame. If a newer render request started while the current one was in-flight, the older result must be discarded. `BeginRequest` starts the epoch, `IsCurrent` guards publication, and `Advance` prepares the next epoch. | ICW-100, ICW-078 | Without this guard, fast camera navigation can commit stale frames after newer viewport state is established, causing visual judder. |
| Drain-queue token liveness | `DrainQueue` (or its replacement) must check claimant-token liveness before promoting a queued item to execution. A queued item whose token has fired must be canceled and skipped, not promoted. | ICW-P0-QUEUE-DRAIN, ADR-0006, External audit validation §1 | Phase 0 delivers the method skeleton; Phase 1 wires real per-frame tokens. Stale-token items must not block usable items behind them or waste concurrency slots. |
| Background noise settings survival | `RegenerateSceneAsync` must not reset user-configured background noise settings. The noise snapshot (target value, noise, circle count, scale, octaves, lacunarity, gain, amplitude) must remain both in the generated scene input and in the bound settings view model across scene regeneration, including automatic startup regeneration. | ICW-151, ICW-P1-SETTINGS-SCOPE | The current Wave A workaround preserves only the generation snapshot. The bound `MainViewModel` still gets replaced and resets the controls, so the invariant remains incomplete until ICW-151 lands. |

## Sprint 1 Wave D additions (2026-07-30)

| Area | Requirement | Related work | Notes |
|---|---|---|---|
| Interest set publication ordering | Interest set publication via `PublishInterestSet` must occur AFTER the per-frame CTS replacement (which fires stale-frame CancellationTokenSources) and BEFORE background tile work starts each frame. The CTS replacement first removes stale claimants; then the interest set culls non-visible queued items. | ICW-143, ADR-0006 | The ordering is: (1) CTS replacement/cancellation, (2) interest set publication, (3) background render work. CTS replacement before interest set is intentional — stale claimants are removed first. |
| Non-visible queued item cancellation | When `PublishInterestSet` is called, any queued (not running) tile work item whose cache key is not in the viewport interest set must be canceled. The failure callback (`onFailed`) must be delivered so the tile can reset its `_generationQueued` flag and retry. | ICW-143, ADR-0006 | Running items are preserved for cache warming. Failure callback delivery is essential — without it, the tile is permanently stuck. See council review bug fix. |
| Visible promotion over prefetch | During `DrainQueueWithLivenessCheck`, when a published interest set contains visible keys, visible items must be promoted over non-visible items. If the dequeued item is not visible, the method scans ahead for a visible candidate. If none exists, the original prefetch item is started. Empty interest set preserves FIFO behavior. | ICW-143, ADR-0006 | The scan-ahead is O(n) under `_lock`. Performance impact tracked by ICW-144. |
| Running items preserved for cache warming | `PublishInterestSet` must NOT cancel in-flight (running) tile generation even if the tile is no longer visible. The pixels may still be useful for cache warming when the viewport returns. | ICW-143, ADR-0006 | Cancellation of running items is driven by claimant-token fire (CTS replacement), not interest set. These are separate mechanisms. |

## Regression review checklist

When a change touches any of the behaviors above, confirm all of the following:

1. The requirement is still reflected in this registry.
2. The relevant task ticket and any impacted ADR remain aligned.
3. Regression coverage or validation evidence exists for the affected behavior.
4. The UX remains consistent with the documented invariant, even if the implementation approach changes.
